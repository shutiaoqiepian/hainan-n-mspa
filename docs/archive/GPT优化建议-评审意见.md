# 对 GPT《火烧云预测算法优化规范》的评审意见

> 评审对象：`docs/火烧云预测算法_AI可读优化规范.md`（2026-10-25，498 行）
> 评审人：本项目维护方
> 结论一句话：**它的诊断是对的，它开的药方这套项目吃不了——因为药方的前提是"有标签数据"，而我们一条都没有。**

---

## 1. 先说结论

| 判断 | 内容 |
|---|---|
| ✅ 对的地方 | 阈值跳变、平滑抹峰、缺失值掩盖、事件概率与出片机会混算——这四个问题都真实存在，我逐项量化了 |
| ⚠️ 不可行的地方 | 云光学厚度/云顶高度/云相态（**数据源根本没有**）、概率校准与机器学习（**没有标签**） |
| ❌ 需要更正的地方 | 它的「现有算法基线概述」是**二手转述**，不是读源码得出的，漏掉了当前最重要的模块 |
| 🔴 我发现的新问题 | **回填反馈的通道在迁到 Cloudflare Pages 之后就失效了**——数据根本进不来，它的整个路线都卡在这一步 |

---

## 2. 我核验通过的一条（可以直接销项）

它 §8 第 2 步要求「对太阳位置函数做独立单元测试，并与可靠的天文算法核对」。做完了：

| 项 | 结果 |
|---|---|
| 方法 | 用 Open-Meteo 的 `daily=sunrise,sunset`（另一套独立实现）当参照，二分求我们 `sunPosition()` 在 `el = −0.833°`（标准折射 + 太阳半径）的过零点 |
| 样本 | 48 组＝4 个纬度（三亚 18.25°N / 海口 20.05°N / 北京 39.90°N / 漠河 52.97°N）× 6 天 × 日出日落 |
| 平均绝对差 | **0.55 分钟** |
| 最大绝对差 | **1.22 分钟** |
| 结论 | 太阳位置函数没有实现错误。这条从待办里划掉 |

## 3. 它说对的四条（我做了量化）

### 3.1 阈值跳变是真的，而且很大

用同一组输入（高云 62 / 中云 20 / 低云 8 / AOD 0.12 / 降水 5% / 湿度 70%），只把某个输入挪过阈值 0.2 个单位：

| 阈值 | 越过前 → 越过后 | 分数跳变 |
|---|---|---|
| **降水概率 40%** | 86 → 61 | **−25** |
| 降水概率 70% | 61 → 39 | −22 |
| 近地面湿度 93% | 71 → 54 | −17 |
| 近地面湿度 88% | 86 → 71 | −15 |
| AOD 0.5 | 74 → 59 | −15 |
| AOD 0.8 | 59 → 45 | −14 |
| AOD 0.3 | 82 → 74 | −8 |
| 高云 55% / 78% | 86 → 86 / 86 → 85 | 0 / −1（这段本来就是连续斜坡） |

**为什么这很要命**：模式每次更新，降水概率从 39% 变成 41%，分数就从 86 掉到 61。
用户看到的是「昨天说能去，今天说别去」，而天气其实没变。这不是精度问题，是**表达问题**。

### 3.2 平滑确实会削峰

当前平滑是 `0.25 × 前一小时 + 0.5 × 本小时 + 0.25 × 后一小时`。
若某个小时单独很好、前后都差（比如 100 / 0 / 0），平滑后只剩 **50**。
短暂但重要的火烧云窗口会被这层平滑抹掉一半。它 §3.8 说对了。

### 3.3 缺失值确实被固定不利值掩盖

现在 `high/mid/low/pop/rh` 缺失时分别填 `90 / 60 / 70 / 60 / 90`，
算完之后用户看到的是一个**看起来很确定的低分**，界面上没有任何「这项没有数据」的提示。
数据完整度是 0 还是 100，页面上完全看不出来。

### 3.4 事件概率与出片机会确实混在一个数里

`faceMatch`（机位朝向）是**直接乘进总分**的。结果是：
一个「天上会烧、但你站的位置拍不到」的黄昏，和一个「天上不会烧」的黄昏，可能显示同一个分数。
它 §3.2 建议把 `event_probability` 与 `photo_opportunity` 分开——这个结构问题是真的。

## 4. 它不成立的三条

### 4.1 「加入云光学厚度、云顶高度、云相态」——数据源根本没有

我直接拿这些变量名去问 Open-Meteo，API 逐个报 `Invalid value`：

```
cloud_top_height      → Invalid value
cloud_base_height     → Invalid value
cloud_optical_depth   → Invalid value
```

当前可用的全部云相关变量只有：`cloud_cover_{low,mid,high}` 和 **气压层上的** `cloud_cover_{1000…200}hPa`。
这正是我们已经在用的东西。

> 想要云光学厚度/云相态，只有三条路：付费 NWP（ECMWF 全分辨率产品）、
> 卫星 L2 产品（Himawari-8/9 云光学厚度，但有时滞、有云检测误差）、或自建反演。
> 这三条都不是「改几行代码」的量级。

它自己在 §3.1 也写了「无直接云光学特征时，将云量作为代理变量，并标记其局限」——
**这正是我们现在在做的事**。所以这条不是「改进建议」，是「现状说明」。

### 4.2 逻辑回归 / 随机森林 / LightGBM / 概率校准——没有标签

项目里**没有任何一条带真实观测的结果记录**（原因见 §5）。
没有标签就没有训练集，没有训练集就没有校准，没有校准就不能输出概率。
它 §3 的第 3 条规则（不得虚构准确率）和第 10 节的结论，其实就是在防这一步——**而它自己给的路线也走不到那一步**。

### 4.3 它的「现有算法基线概述」是二手转述，漏了主模块

它 §2 列的 10 个模块（`fHigh`…`finalScore`）是**从我们给它的文档里转述的**，不是读源码得出的。
漏掉了当前真正在做判断的两个东西：

| 被漏掉的 | 作用 | 规模 |
|---|---|---|
| `clouds.ts` → `cloudProfile()` | 用 8 个气压层的云量/湿度/温度/位势高度推**云属**（Ci/Cs/Ac/As/Sc/St/Cu/Cb…）、云底、云顶、是否"薄云能被低角度阳光从下方照亮" | 384 行 |
| `api.ts` → `syntheticProfile()` | 无剖面数据时按三层云量兜底生成云层 | — |

**「能不能烧」很大程度上取决于云是什么云**，而不是三个层云量的百分比。
如果按它 §2 的模块清单去"优化"，会漏掉这一块，只在小数点上打转。

> 这一条也提醒：给 AI 的摘要越简略，它提出的方案就越容易偏。
> 我上一版《给GPT-火烧云算法》只抽了评分链路，`cloudProfile` 也只在文字里提了一句，这是我的责任。

## 5. 🔴 我发现的新问题：反馈通道已经失效

它整个路线的第一步是「收集标签」。但我们现在的标签收集是断的：

| 现状 | 问题 |
|---|---|
| `feedback.ts` 把回填结果 `POST /` 提交 | 这是 **Netlify Forms** 的提交方式 |
| 站点已迁到 **Cloudflare Pages** | Cloudflare 没有 Forms 功能，`POST /` 返回错误 |
| 失败后的兜底 | 存进**用户自己的 localStorage** + 复制一段文字让用户手动发 |

**结果：管理员一条数据也收不到。** 用户以为提交了，其实只存在他自己手机里，
而且换个设备就没了。页面上从 2026-10-21 迁站到现在，可能一条有效反馈都没进后台。

这才是「无法回测」的真正原因——不是我们不想收集，是**收集通道坏了**。

## 6. 行动清单（按「要不要改分数」分档）

### A 档：不改分数的结构改进（建议现在做，约 2–3 小时）

| # | 做什么 | 解决它哪条 |
|---|---|---|
| A1 | **修复反馈落库**：换成 Workers + KV / D1，或接 Supabase 表 | 一切的前提 |
| A2 | 每行输出 `data_completeness`，缺关键项时页面标「数据不全 · 仅供参考」 | §3.7 |
| A3 | 环境分与出片机会**分开显示**（两个数，不是一个乘完的数） | §3.2 |
| A4 | 详情里同时给「平滑后」与「原始逐时」两条线 | §3.8 |
| A5 | 把太阳位置核验写成仓库内离线测试（48 组快照） | §8 第 2 步 |

### B 档：会改分数，必须留 baseline 对照（建议做，但要能 A/B）

| # | 做什么 | 风险 |
|---|---|---|
| B1 | 降水/湿度/AOD 阈值**连续化**（单调样条插值） | 会整体改分数水平。我用对数插值试过，AOD 0.15 的系数从 0.97 掉到 0.86，分数直接掉 12 分——必须做**等均值校准**，不能直接换 |
| B2 | 缺失值改为「不参与打分 + 放大不确定性」 | 缺数据时的分数会明显变化 |
| B3 | 平滑降级为「只用于展示」，分数用原始逐时 | 峰谷都会变陡，Top 榜会变 |

**做法**：B 档每项都做成开关，能一键切回当前公式，用同一批历史缓存跑对照，看排序变化率。

### C 档：必须有标签才能做（现在做不了）

概率校准（Platt/Isotonic）、Brier/PR-AUC/可靠性图、逻辑回归/GBDT、按提前量分层校准。
这些全部依赖 A1 修好 + 攒够样本（我的判断：**至少 200 条带"没烧"的负样本**，否则类别极不平衡，PR-AUC 没有意义）。

## 7. 我对它整体方案的判断

它的**方法论是对的**：冻结 baseline → 区分证据等级 → 用时间外测试验证 → 不虚构准确率。
这套纪律应该照收。

它的**技术路线不适配本项目的资源约束**：
它按「有完整云微物理数据 + 有历史标签 + 可训练模型」的理想项目写方案，
而现实是「免费 API + 静态站 + 0 条标签」。

所以我的建议是：

1. **先按 A 档做**（尤其 A1），把数据通道修好；
2. **B1 只做一件**（阈值连续化），做完留开关、跑对照；
3. **C 档整体推迟**，等样本再说；
4. 页面上把当前版本标成 **「v1 启发式 · 未校准」**，
   并在方法说明里写明「分数是相对排序，不是发生概率」——这句现在站上已经有了，保持住。

> 一句话：**它给的是研究生课题，我们现在需要的是一间能采样的实验室。**
> 先把门修好，再谈算法。
