## 0. 一句话说明它是什么

输入**某个地点某个时刻的三层云量、气溶胶光学厚度、降雨概率、湿度、能见度**，
输出一个 **0–96 的「霞光指数」**，并映射成「火烧云 / 大烧 / 中烧 / 小烧 / 微烧 / 不烧」六档。

**它不是天气预报。** 它是「这个黄昏值不值得专门跑一趟机位」的启发式排序工具。
请把这个定位写进任何使用它的产品里（原作者页面上的原话：「仅供参考，别当天气预报用」）。

## 1. 输入数据结构

```ts
/** 某一小时的观测集合。所有值是「同一小时的」；多模式时调用方已做好平均。 */
interface Measure {
  high: number | null   // 高云量 %（0–100），云量来自模式预报
  mid: number | null    // 中云量 %
  low: number | null    // 低云量 %
  rh: number | null     // 2 m 相对湿度 %
  pop: number | null    // 降水概率 %
  t2m: number | null    // 2 m 气温 ℃
  td2m: number | null   // 2 m 露点 ℃
  vis: number | null    // 能见度 m（注意单位是米）
  aod: number           // 550 nm 气溶胶光学厚度（无量纲），必填，缺省用 0.2
}

interface SunPos { el: number; az: number }   // 太阳高度角 / 方位角，度；az 正北 0 顺时针
```

**`null` 表示「没有数据」，不表示 0。** 评分函数对缺数据有专门的保守处理（见 §4）。

## 2. 太阳位置（NOAA 低精度解析式）

这一步是**纯几何**，不涉及任何经验参数，可以直接照抄。

```ts
export function sunPosition(timeMs: number, latDeg: number, lonDeg: number): SunPos {
  const rad = Math.PI / 180
  const n = timeMs / 86400000 + 2440587.5 - 2451545.0

  const L = ((280.46 + 0.9856474 * n) % 360 + 360) % 360      // 平黄经
  const g = ((357.528 + 0.9856003 * n) % 360 + 360) % 360     // 平近点角
  const lambda = (L + 1.915 * Math.sin(g * rad) + 0.02 * Math.sin(2 * g * rad)) * rad
  const eps = (23.439 - 0.0000004 * n) * rad                  // 黄赤交角

  const dec = Math.asin(Math.sin(eps) * Math.sin(lambda))     // 赤纬
  const ra = Math.atan2(Math.cos(eps) * Math.sin(lambda), Math.cos(lambda)) // 赤经

  const gmst = ((280.46061837 + 360.98564736629 * n) % 360 + 360) % 360
  const lst = ((gmst + lonDeg) % 360 + 360) * rad             // 地方恒星时
  const ha = lst - ra                                          // 时角

  const latR = latDeg * rad
  let sinEl = Math.sin(latR) * Math.sin(dec) + Math.cos(latR) * Math.cos(dec) * Math.cos(ha)
  sinEl = Math.max(-1, Math.min(1, sinEl))

  const el = Math.asin(sinEl)
  const cosEl = Math.cos(el) || 1e-6

  const sinA = -Math.cos(dec) * Math.sin(ha) / cosEl
  const cosA = (Math.sin(dec) - sinEl * Math.sin(latR)) / (cosEl * Math.cos(latR))
  let az = Math.atan2(sinA, cosA) / rad
  if (az < 0) az += 360

  return { el: el / rad, az }
}
```

精度约 1 角分，做霞光判断完全够用。`timeMs` 是 UTC 毫秒时间戳。

## 3. 核心评分

```ts
function clamp(v: number, a: number, b: number): number {
  return Math.max(a, Math.min(b, v))
}

/* 高云是火烧云的「画布」。最佳区间 55–78%。 */
export function fHigh(h: number): number {
  if (h < 8) return 0                          // 几乎没有高云 → 没东西可烧
  if (h <= 55) return (h - 8) / 47             // 8%→0，55%→1 的缓坡
  if (h <= 78) return 1                        // 最佳窗口
  return 0.25 + 0.75 * (100 - h) / 22          // >78% 多为厚层云，反而挡光
}

/* 低云挡地平线，越少越好 */
export function fLow(l: number): number {
  return clamp(1 - l / 82, 0, 1)
}

/* 中云适中最好，太厚会盖住 */
export function fMid(m: number): number {
  if (m <= 55) return 1
  return clamp(1 - (m - 55) / 40, 0, 1)
}

export function fAod(a: number): number {
  return aodBand(a).v
}

/* 下雨、起雾都不利 */
export function fWet(pop: number, rh: number): number {
  const p = pop < 40 ? 1 : pop < 70 ? 0.62 : 0.22
  const r = rh > 93 ? 0.5 : rh > 88 ? 0.78 : 1
  return p * r
}

export function scoreOf(m: Measure): number {
  // 缺数据时按「最不利」处理：宁可低估，也不虚高
  const high = m.high == null ? 90 : m.high
  const mid  = m.mid  == null ? 60 : m.mid
  const low  = m.low  == null ? 70 : m.low
  const pop  = m.pop  == null ? 60 : m.pop
  const rh   = m.rh   == null ? 90 : m.rh

  const h = clamp(fHigh(high), 0, 1)
  if (h <= 0) return 0

  const lowF = 0.3  + 0.7  * fLow(low)
  const midF = 0.72 + 0.28 * fMid(mid)
  const aodF = 0.55 + 0.45 * fAod(m.aod ?? 0.4)
  const wetF = 0.55 + 0.45 * fWet(pop, rh)

  const raw = h * lowF * midF * aodF * wetF
  const score = 100 * Math.pow(clamp(raw, 0, 1), 1.8)

  return Math.round(Math.min(96, score))
}
```

## 4. 设计取舍（**这是最容易做错的部分，务必读完**）

### 4.1 为什么是乘法，不是加权平均
早期版本用 `0.35*高云F + 0.25*低云F + ...` 的加权和，结果是：**海南任何一天晴天都能给到 90 分**。
因为低云、中云、AOD 在多数日子都是「还不错」的中间值，加权和把它们平均起来，分数几乎只跟着高云量走。

改成乘法后，任何一项差都会**把总分整体压下去**，不会被别的项补回来。
再用 `^1.8` 整体压缩：条件「都还不错」也压不到高分，必须「每一项都很好」才上 80。

### 4.2 为什么上限是 96，不是 100
模式对云量的 1 天预报相关系数（TCC）只有 **0.47**（CMA-BJ 系统检验，见 §7）。
一个永远够不着 100 的分制，比一个经常给 100 的分制诚实。

### 4.3 为什么高云 < 8% 直接归零
火烧云需要云当「画布」；一片晴空只能出渐变天色，没有你可以拍的「烧」。
8% 是给模式漏报薄卷云留的余量（模式会高估「无云」频率，见 MetCoOp 检验），
但阈值仍取 8% 而不是 0 —— 低于 8% 时即使真有少量卷云，也烧不起来。

### 4.4 缺数据为什么按「最不利」填
`high=90, mid=60, low=70, pop=60, rh=90`。
看起来「高云 90 是好事」，但 `fHigh(90)=0.59`，配合 `fLow(70)=0.15` 之类的低分项，整体会被压低。
这是刻意的：**宁可漏报，不可误报**。用户跑一趟机位的成本，比错过一次高得多。

### 4.5 完整流水线（**这才是「优化后」的算法**，逐行取自 `api.ts`）

`scoreOf()` 只是第一步。项目真正显示给用户的分数，是下面这条流水线的结果。
**只搬 `scoreOf()` 会得到明显偏高的分数**，因为少了后面四层压制。

```ts
/* ① 三个模式各算一遍，用离散度当「可信度」 */
let perModel: number[] = []
mids.forEach((mid) => {
  const mm = measureAt(w, airObj, idx, [mid])
  if (mm.high == null) return              // 这个模式没给数据，不参与统计
  perModel.push(scoreOf(mm))
})
if (!perModel.length) perModel = [scoreOf(m)]

const mean = perModel.reduce((a, b) => a + b, 0) / perModel.length
const variance = perModel.reduce((a, b) => a + (b - mean) * (b - mean), 0) / perModel.length
const spread = Math.round(Math.sqrt(variance))

/* ② 逐时平滑：避免分数在整点之间跳变 */
const s1 = scoreOf(m)
const sPrev = idx > 0 ? scoreOf(measureAt(w, airObj, idx - 1, mids)) : s1
const sNext = idx < times.length - 1 ? scoreOf(measureAt(w, airObj, idx + 1, mids)) : s1

let score = 0.25 * sPrev + 0.5 * s1 + 0.25 * sNext

/* ③ 模式分歧越大，分数越不可信 → 直接打折（最多扣 28%） */
if (mids.length > 1) {
  score = score * (1 - Math.min(0.28, spread / 55))
}

/* ④ 机位朝向：太阳不在你能看见的方向，分再高也拍不到 */
if (sun) score = Math.round(score * face)   // face = faceMatch(spot, sun.az)

/* ⑤ 高空湿度剖面修正（低云封挡 / 高层有云，见下表） */
const prof = profileOf(pr, idx)
if (prof) score = clamp(Math.round(score * prof.mod), 0, 100)

/* ⑥ 时效折扣：明天乘 0.95（48 h 后模式技巧快速下降） */
if (state.day === 1) score = Math.round(score * 0.95)

/* ⑦ 硬上限 96 */
score = clamp(score, 0, 96)
```

**⑤ 用到的 `profileOf` 修正系数**（各气压层相对湿度判云在哪一层）：

```ts
// 850 hPa ≈ 1500 m、700 ≈ 3000 m、500 ≈ 5500 m、400 ≈ 7200 m
function profileOf(rh850: number|null, rh700: number|null, rh500: number|null, rh400: number|null, blh: number|null) {
  const lowWet  = rh850 != null && rh850 >= 80
  const midWet  = rh700 != null && rh700 >= 80
  const highWet = (rh500 != null && rh500 >= 60) || (rh400 != null && rh400 >= 60)

  let label: string, mod: number
  if (lowWet && highWet)      { label = '低云封挡，高云被遮'; mod = 0.72 }
  else if (lowWet)            { label = '低层潮湿，地平线不清'; mod = 0.82 }
  else if (highWet)           { label = '高层有云、低层干爽'; mod = 1.10 }
  else if (midWet)            { label = '中层有云，高层偏干'; mod = 0.95 }
  else                        { label = '各层偏干，本就不易有霞'; mod = 0.90 }

  /* 边界层很浅：霾和雾贴着地面，低角度视野差 */
  if (blh != null && blh < 350 && mod > 0.7) { label += ' · 边界层浅'; mod *= 0.94 }

  return { label, mod }
}
```

**④ 的朝向匹配：**

```ts
const FACE_AZ = { 西: 270, 西南: 235, 南: 180, 东南: 135, 东: 90, 西北: 305, 北: 0 }

function faceMatch(face: string, az: number): number {
  const center = FACE_AZ[face]
  if (center == null) return 0.9          // 山顶等不限方向
  let d = Math.abs(((az - center) % 360 + 360) % 360)
  if (d > 180) d = 360 - d
  return 0.55 + 0.45 * clamp(1 - d / 110, 0, 1)
}
```

**这一层有多重要（用真实缓存数据实测）**：

拿仓库里 `data/forecast/hn.json`（2026-10-24 18:16 那次缓存）跑一遍，对比「只用 `scoreOf`」和「走完整流水线」：

| 机位 | 只看 `scoreOf` | 页面上实际显示 | 差额 | 模式分歧 spread |
|---|---|---|---|---|
| 临高角 | 84 | **51** | −33 | 35 |
| 海口西海岸观海台 | 81 | **46** | −35 | 32 |
| 海口假日海滩 | 81 | **46** | −35 | 32 |
| 乐东龙沐湾 | 79 | **55** | −24 | 10 |
| 东方鱼鳞洲 | 68 | **61** | −7 | 3 |

也就是说：**只搬 `scoreOf()` 会把「中烧」报成「大烧」**，因为缺了模式分歧折扣和剖面修正。
这正是改造前「动不动大烧」的老毛病，也正是这一版把 1.8 次方 + 四层压制叠上去的原因。

## 6. 已知局限（照实说，别包装）

| 限制 | 后果 |
|---|---|
| 没有**云底高度 / 云水含量 / 云的相态** | 无法区分「薄卷云」和「厚高积云」的透光差异，判断精度不如专业服务 |
| 模式网格 6–28 km | 同一城市几个机位常共享一份数据，显示相同是正常的，不是 bug |
| 云量 TCC ≈ 0.47（1 天时效） | 分数只能当**相对排序**用，绝对值不可当真 |
| 没有历史回测 | 全部阈值是「物理原理 + 摄影经验」推出来的启发式，**未做拟合或验证** |
| 气溶胶数据的空间分辨率更粗 | AOD 只能反映大范围通透度，山区局地霾判断不了 |

## 8. 一句话交给别的模型的提示词

> 这是一套给摄影用的「火烧云值不值得跑一趟」启发式评分，不是天气预报。
> 核心是五个因子的**乘法**（高云画布、低云遮挡、中云遮挡、气溶胶通透度、降水湿度），

> 全部阈值是物理原理 + 经验推出来的，未做回测，只能当相对排序用。
