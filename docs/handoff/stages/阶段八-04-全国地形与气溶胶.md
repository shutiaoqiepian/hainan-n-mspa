## 1. 做了什么

`tools/xsec/build_context.py` 扩展为**支持全国索引与批量合并请求**：

| 改动 | 说明 |
|---|---|
| `--index` | 可指定 `national-index.json`；经纬度从机位文件读（索引里没有 lat/lon） |
| `--batch N` | 相邻 N 个机位的 DEM 采样点**合并成 ≤100 坐标的请求**（实测 6 个机位 1 716 个坐标 → 18 次请求） |
| `--skip-existing` | 断点续跑：已有结果的机位跳过，不重复请求 |
| 太阳方位地形去重 | 每机位只存**日落方位**那一份（4 个时次方位差 <3.2°），体积降到 1/4，页面标注"其余时次复用" |
| 主备源重试 | Open-Meteo 被限流（429）→ 切 SRTM；SRTM 也失败 → **下一批重新试主源**（否则一旦回退就永远用慢的备源） |
| AOD 独立失败 | DEM 拿到就写，AOD 失败记缺测，不拖垮整个机位 |

---

## 2. 为什么这件事这么慢（如实记录）

| 环节 | 实测 |
|---|---|
| Open-Meteo 海拔接口免费额度 | 同一出口 IP **约 10 次/分钟**，跑几十批后会被**按小时封顶**（`429 Hourly API request limit exceeded`） |
| 回退源 OpenTopoData SRTM | 单次最多 100 点、公共接口限 1 次/秒，且大请求经常**超时**（已把单段降到 50 点、超时 90 s） |
| 每机位请求量 | DEM 打包后约 3 次/机位 + AOD 1 次 = **4 次** |
| 224 机位总请求 | 约 **900 次** → 按 10 次/分钟要 90 分钟，被限额打断后更久 |

**这不是"技术上做不到"，是免费额度的物理限制。** 已完成的机位会逐个写进
`data/cross/national-context.json`（每批落盘一次），可以反复续跑到 224/224。

## 4. 当前进度与如何继续

```
python tools/xsec/build_context.py --index data/cross/national-index.json \
    --out data/cross/national-context.json --batch 4 --skip-existing --allow-partial
```

- 每批写一次盘、跳过已完成机位，可以随时中断再续；
- 完成后 `national-context.json` 里应有 224 个机位；`errors[]` 记录失败原因（不会伪造数据）；
- 页面无需改动，刷新即生效。

**实测进度（2026-11-01 15:40）**：`national-context.json` 已补齐 **45 / 224** 个机位
（Copernicus GLO-30 31 个、SRTM 回退 14 个），其余因两源同时限流暂未完成。
加固后的行为：连续 16 批失败就提前退出并落盘（返回码 2），不再逐条记成失败；
重跑同一条命令会跳过已完成的机位继续。

**诚实说明**：本文写作时该任务仍在跑（已完成的机位见 `national-context.json` 的键数）。
在跑满 224 之前，**全国机位的地形仍是模式地形、AOD 仍是缺测**，
界面上也照实这么标注——不因为"计划要做"就提前写成已完成。
