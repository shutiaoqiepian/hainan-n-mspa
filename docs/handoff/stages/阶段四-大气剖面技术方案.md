## 0. 先把概念钉死（任务书 3.1 的核心要求）

任务书明确区分两种图，我完全同意，并且认为这是整份任务书里最该守住的一条：

### A. 垂直廓线（Vertical Profile）

- 横轴：气象变量（或时间）
- 纵轴：高度 / 气压
- 数据：**某一个格点**在垂直方向上的 N 个值
- 物理意义：这个地点头顶的大气柱长什么样

**我们线上现在有的就是这个**（`SpotPanel.vue` 的 8 行云层表）。
8 个气压层 × 1 个格点。它没有任何水平空间信息。

### B. 水平—垂直截面（Cross Section）

- 横轴：**从观测点沿某方位角延伸的水平距离**（km）
- 纵轴：海拔高度（km）
- 数据：沿路径 M 个空间点 × N 个气压层
- 物理意义：某个时刻，沿某个方向切开大气，看到的一条断面

**我们没有这个。** 任务书 3.1 说得很对：

> 不能把单个地点的垂直廓线直接包装成真实的水平—垂直截面。

所以这件事不能「在现有剖面上加个横轴」糊弄过去，必须真的沿路径取多个点。

## 1. 空间采样设计

### 1.1 采样路径

```
起点：机位 (lat0, lon0, elev0)
方位角：az（默认 265° 西偏南，即日落方向；可调 0–359°）
长度：D（默认 50 km；可选 100 / 200 km）
采样间隔：Δd
第 i 个采样点：沿 az 方向距离 i·Δd
   的经纬度（球面大圆近似即可，50 km 内误差可忽略）
```

### 1.2 采样间隔必须服从数据分辨率，不能拍脑袋

GFS 0.25° 在海南附近：
- 纬向 0.25° ≈ 27.8 km
- 经向 0.25° ≈ 26.1 km（19°N）

**硬规则：采样间隔 = 数据格距的一半（Nyquist），再多就是编造细节。**

| 数据源 | 格距 | 采样间隔 | 50 km 内的采样点数 |
|---|---|---|---|
| GFS 0.25° | ≈27 km | **13.5 km** | 5 个 |
| ECMWF 0.1° | ≈11 km | 5.5 km | 10 个 |
| ECMWF 0.25° | ≈27 km | 13.5 km | 5 个 |

**50 km 只有 5 个采样点。这就是现实。**

所以：
- 剖面图的横轴不是「连续像素」，而是 **5 个格点 + 它们之间的双线性插值**
- 图上**必须画出这 5 个真实格点的位置标记**（小竖虚线），让用户看见
  「哪几处是真数据、哪几处是插值出来的」
- 图例或角标写明：`横向分辨率 ≈27 km（GFS 0.25°）｜灰虚线 = 真实格点`

任务书 3.2 原话：「插值只能获得网格之间的估计值，不代表真实观测。
必须保留原始网格分辨率信息，不能将插值结果误认为高分辨率实测数据。」
—— 上面这套就是它的实现方式。

### 1.3 取数据的两种实现路径

**路径一（推荐，先做）：Open-Meteo 多点请求**

Open-Meteo 支持一次传多个坐标。沿路径取 5 个点 = 1 次请求。
- 优点：立刻能跑，不用碰 GRIB，今天就能做原型
- 缺点：云量是 RH 诊断值 → 图上必须标「估算云」

**路径二（真正专业）：GFS GRIB 按字节范围取**

```
1. 拉 .idx（几 KB）
2. 解析出需要的 (变量, 层) 的字节区间
3. 对每个区间发 Range 请求（实测单层 0.16–0.36 MB）
4. eccodes / cfgrib 解析 → 裁剪到海南附近 10×10 格
5. 沿路径做双线性插值
6. 写紧凑 JSON 进 data/cross/
```
- 优点：拿到**真实的云水 + 云冰**，剖面才有物理意义
- 缺点：需要 GitHub Action + Python

**建议：先路径一做原型，验证交互和几何；再切路径二拿真数据。**
理由：路径一的产物（几何、交互、太阳投影）在切到路径二时可以 100% 复用，
只有「数据来源」那一层换掉。这样风险最低。

## 2. 垂直坐标（任务书 3.3，这里最容易出错）

任务书列了 6 条要求，逐条给出实现：

### 2.1 气压 ≠ 高度，而且同一个气压层在不同位置高度不同

实测证据（同一时刻，海南不同位置 850 hPa 的位势高度）：

| 位置 | 850 hPa 位势高度 |
|---|---|
| 海口 | 1537 m |
| 三亚 | 1549 m |

差 12 m。冷空气来的时候差得更多（可达 50–80 m）。

**所以绝对不能「用一张固定高度表把所有气压层换算完」。**

### 2.2 正确做法

```
每个 (格点, 气压层) 都用该点自己的 geopotential_height_{L}hPa
作为它的真实高度坐标 —— 直接取，不换算。
```

GFS 有 `HGT`（位势高度）22 层，Open-Meteo 有 `geopotential_height_{L}hPa` 17 层。
两者都是**逐格点逐层**给的，这是最准的来源，零假设。

只有数据缺这个字段时才退而用压高公式：
```
z = z₀ + (R·T̄/g)·ln(p₀/p)     R=287.05, g=9.80665, T̄ 取该层平均温度
```
且必须在图上标注「高度为压高公式换算，非模式位势高度」。

### 2.3 地形：低于地表的气压层不能画到地下

实测（海南 850 hPa 高度 1537 m，地面气压约 1006 hPa）：
- 1000 hPa 层在海拔 **约 200 m** 处 → 海南岛大部分陆地（几十米）在它下面 ✅ 可用
- 五指山海拔 1867 m → 对它来说 1000/975/950/925 层都可能在地表以下 ❌ 必须剔除

实现（这是个能自动兜住的工具函数）：

```js
// 对每个 (格点, 层)：如果 该层位势高度 <= 该格点地形高度，标记为地下
for (const point of path) {
  for (const level of levels) {
    const z = level.geopotential_height
    if (z == null) { level.status = 'missing'; continue }
    if (z <= point.terrainElev + 5) { level.status = 'underground'; continue }
    level.status = 'ok'
  }
}
```

渲染时 `underground` 的格子填成地形色（不是空白、不是 0），
悬浮提示显示「此层低于地表（地形 xxx m）」。
**这是最容易画错的地方：把地下层画成透明，会让人以为那里是晴空。**

### 2.4 高度轴范围

- 下限：0 km（海平面）
- 上限默认 **16 km**（覆盖对流层顶 + 高云；海南积雨云顶可达 16–17 km）
- 可切到 8 km（只看低/中云）和 22 km（看平流层）

### 2.5 为什么不支持「模式层」

GFS 的 `hybrid level`（我们实测索引里 CLWMR 有 1 条 hybrid level）需要
配套的 `Vcoord`（模式层系数 a/b）才能换算成气压。GFS 的 hybrid 系数在
单独的 `gfs.tHHz.pgrb2.0p25.f000` 或 `atmos/` 下的其他文件里。
**本项目用不到**（气压层已经够），所以明确不支持，避免半吊子实现。

## 3. 云层识别（任务书 3.5，这是「不能糊弄」的核心）

### 3.1 三个等级，明确标注

| 等级 | 依据 | 我们能不能做到 | 界面标注 |
|---|---|---|---|
| **第一优先** | 模式三维云水 `CLWMR` + 云冰 `ICMR` | ✅ GFS 能拿到 | **不标「估算」**，标「模式云水/云冰场」 |
| **第二优先** | 有算法依据的云量诊断 | ⚠️ 需要自己实现云方案 | 标注阈值和算法名 |
| **第三优先** | 相对湿度估算 | ✅ Open-Meteo 的压力层云量就是这种 | **必须标「估算」** |

### 3.2 用云水/云冰判定云区的具体阈值

物理上「有没有云」= 云水/云冰混合比是否超过一个下限。
GFS 的 CLWMR/ICMR 单位是 **kg/kg**。典型量级：

| 情况 | 混合比 |
|---|---|
| 晴空（数值噪声级） | < 10⁻⁵ kg/kg |
| 淡薄云 / 云边缘 | 10⁻⁵ ~ 10⁻⁴ |
| 明显云 | 10⁻⁴ ~ 10⁻³ |
| 浓密云 / 积雨云 | > 10⁻³ |

**初版阈值（必须用实测数据校准后才能定稿）：**

```
云区判定：CLWMR + ICMR >= 1e-5 kg/kg
  淡云：1e-5 ~ 1e-4
  中云：1e-4 ~ 5e-4
  浓云：> 5e-4
```

⚠️ 这三个数**现在是假设，不是结论**。落地第一步必须是：
拿一天的 GFS 数据，统计海南区域 CLWMR 的实际分布（分位数），
再用 ERA5 的同类字段对照量级，确认 1e-5 这个门槛合理，
然后才写进代码和文档。**在实测校准前，这三个数不能对外说。**

### 3.3 云水 ≠ 云冰 ≠ 降水

GFS 索引里同时有：
- `CLWMR` 云水、`ICMR` 云冰 → 属于「云」
- `RWMR` 雨、`SNMR` 雪、`GRLE` 霰 → 属于「降水粒子」，**不是云**

必须分开画：
- 云水 → 一种色阶（蓝绿系）
- 云冰 → 另一种色阶（紫白系）
- 降水粒子默认不画（可选图层，且要提示「这是降水不是云」）

任务书 3.4 原话：「需要区分云水、云冰、降水水物质和云量，
不允许将不同物理量混为一谈。」—— 上面就是它的落地方式。

### 3.4 用 Open-Meteo 时的降级（路径一阶段）

只能用 `cloud_cover_{L}hPa`，且**已实测确认它是 RH 诊断值**
（RH<40% 恒为 0，RH≥100% 才 91%）。

界面上必须同时出现这三句话，缺一不可：
1. `云量为相对湿度诊断估算，非模式原生云场`
2. `依据：相对湿度（阈值见下）`
3. `估算局限：无法区分云水/云冰；高湿但无云时可能误判为有云`

**已实测的误判风险**：RH 60% 的桶里云量极差 28 个百分点、
RH 90% 的桶里极差 44 个百分点 —— 同一个湿度下有没有云差别很大。
这正是「不能只看 RH 阈值」的证据。

## 4. 太阳几何（任务书 3.7，这里有个非常容易错的地方）

### 4.1 先算太阳位置

已有实现 `src/lib/forecast/sun.ts`（日出日落、方位角、高度角都现成），
剖面直接复用，不重写。

### 4.2 关键：太阳方位角 ≠ 剖面方位角

**这是本方案最容易做错的一点。**

剖面是沿方位角 `az` 切开的一个**竖直平面**。
太阳方位角 `sunAz` 只有在 `|sunAz - az|` 很小时，太阳才大致落在这个平面里。

一般情况：

```
太阳方向单位矢量（以观测点为原点，东 x、北 y、上 z）：
  s = (cos(el)·sin(az_s), cos(el)·cos(az_s), sin(el))

剖面平面：由水平方向 u = (sin(az), cos(az), 0) 和竖直方向 k = (0,0,1) 张成
```

**太阳在该平面内的投影：**

```
s‖ = s 在 u 上的分量 = cos(el)·[sin(az_s)sin(az) + cos(az_s)cos(az)]
                     = cos(el)·cos(az_s − az)
s⊥ = 平面外的分量     = cos(el)·sin(az_s − az)

平面内（水平, 垂直）= ( s‖ , sin(el) )
```

于是「太阳光线在剖面图上的倾角」= `atan2(sin(el), s‖)`
—— **不是** `el` 这个太阳高度角本身！

举例（海南日落，el = 2°，sunAz = 265°，剖面 az = 265°）：
- `az_s − az = 0` → `s‖ = cos(2°) ≈ 0.999` → 图上倾角 ≈ `atan2(0.035, 0.999)` ≈ **2°**
  → 太阳几乎在图的右边缘、光线近乎水平 ✅ 符合直觉

再举例（剖面 az 取 180° 正南，太阳仍 265°）：
- `az_s − az = 85°` → `s‖ = cos(2°)·cos(85°) ≈ 0.087` → 倾角 ≈ `atan2(0.035, 0.087)` ≈ **22°**
- 而且 `s⊥ ≈ 0.046`，说明**太阳大部分不在这个平面里**

**必做的界面处理：**

```
if |az_s − az| > 15°:
    画出太阳符号，但加一句提示：
    「太阳方位 265°，与本剖面 180° 相差 85° ——
      太阳不在剖面内，图中的光线方向仅为投影」
    并且把太阳符号画淡（降低不透明度）
else:
    太阳正常投影，光线可画成实线
```

**绝不能把太阳随手放在图上一处然后画几条斜线就说是「光照关系」。**

### 4.3 几何照射 ≠ 辐射传输（任务书明确要求区分）

界面上要区分三个层次，用不同的视觉语言：

| 层次 | 怎么画 | 措辞 |
|---|---|---|
| 几何遮挡 | 从太阳位置向云层画直线，标出哪段路径穿过云 | 「几何上，这条视线穿过 850–700 hPa 的云」 |
| 云场 | 云水/云冰色块 | 「模式云水场」 |
| 辐射传输 | **不做**，或明确写「未做」 | 「本图未进行辐射传输计算」 |

任务书 3.7 原话：「太阳光线可以作为几何参考线展示，
但不能把简单的射线交点当作真实的云层辐射传输模拟。」

**这条我完全同意，并且认为比图好不好看重要得多。**
颜色标注「这层云会被照成橙金」是现有 `DecisionHero` 的 `vividLabel` 干的活，
那是**业务算法的输出**，不是剖面图算出来的。两者不能混。

## 5. 数据结构（任务书第五部分要求）

```ts
/* 一条剖面 = 一个机位 × 一个方位 × 一个长度 × 一个时刻 × 一个模式 */
interface CrossSection {
  // ---- 身份与溯源（每一张图都必须能回答「这数据哪来的」）----
  source: 'gfs_pgrb2_0p25' | 'openmeteo_diag' | 'ecmwf_od'
  model: string                 // 'gfs_seamless' / 'ecmwf_ifs025'
  modelRunTime: string          // 起报时间 ISO，如 '2026-11-01T12:00:00Z'
  validTime: string             // 有效时间 ISO
  forecastLeadHours: number     // 预报时效
  generatedAt: string           // 数据抓取时间

  // ---- 空间几何 ----
  origin: { lat: number; lon: number; elev: number; name: string }
  azimuthDeg: number            // 剖面方位角
  lengthKm: number              // 剖面长度
  gridResolutionKm: number      // 数据真实格距 —— 必须显示在图上
  sampleIntervalKm: number      // 采样间隔（= 格距/2）

  // ---- 横轴：沿路径的采样点 ----
  samples: Array<{
    index: number
    distanceKm: number
    lat: number
    lon: number
    terrainElevM: number        // 该点地形高度（用来判断哪些层在地下）
    isRealGridPoint: boolean    // true = 恰好落在模式格点上；false = 插值点
  }>

  // ---- 纵轴：气压层 ----
  levels: number[]              // [1000, 925, 850, 700, 600, 500, 400, 300, 200]

  // ---- 主数据：二维场 [levelIdx][sampleIdx] ----
  fields: {
    geopotentialHeightM: (number | null)[][]   // 该层在该点的真实高度（纵坐标来源）
    temperatureC:        (number | null)[][]
    relativeHumidity:    (number | null)[][]
    cloudWaterKgKg:      (number | null)[][]   // CLWMR，没有就是 null（不是 0！）
    cloudIceKgKg:        (number | null)[][]   // ICMR
    cloudFraction:       (number | null)[][]   // 只有诊断源才有；GFS 无
    uWindMs:             (number | null)[][]
    vWindMs:             (number | null)[][]
    verticalVelocityHpa: (number | null)[][]   // 注意单位！Pa/s 还是 m/s
  }

  // ---- 质量标记 ----
  quality: {
    cloudIsEstimate: boolean            // 云是否为 RH 估算
    cloudMethod?: string                // 估算方法说明（估算时必填）
    cloudThresholdPct?: number          // 估算用的阈值
    hasCloudWater: boolean              // 是否有真实云水
    hasCloudIce: boolean                // 是否有真实云冰
    interpolatedHorizontally: true      // 水平方向一定经过插值
    undergroundCells: Array<[number, number]>   // 低于地表的格子
    missingCells: Array<[number, number]>
    notes: string[]
  }

  // ---- 太阳几何 ----
  sun: {
    elevationDeg: number
    azimuthDeg: number
    sunriseLocal: string
    sunsetLocal: string
    // 太阳在剖面平面内的投影（见 §4.2）
    inPlaneHorizontal: number     // s‖
    inPlaneVertical: number       // sin(el)
    planeAngleDeg: number         // atan2(垂直, 水平)
    offPlaneAngleDeg: number      // |az_s - az|，>15° 要提示
  }
}
```

### 5.1 为什么缺失必须是 `null` 而不是 `0`

云水混合比 0 是「绝对没有云」这个**强断言**；
`null` 是「没有这个数据」。两者混淆会让图上出现假的晴空区。
现有代码在 `qualityOf()` 里已经坚持这个原则（缺测不填默认值），剖面沿用。

### 5.2 单位必须写在字段名里

`verticalVelocityHpa` 这个命名是刻意的 —— GFS 的 VVEL 单位是 **Pa/s**，
Open-Meteo 的 `vertical_velocity_{L}hPa` 实测标的是 **m/s**（差约 10 倍量级）。
两个源混用时，靠字段名强制自己别写错。

## 6. 数据处理管线

```
[GitHub Action，每天 2 次（日落前 2 小时 + 凌晨校准）]

1. 选机位：只要 top N（先取海南 8 个代表机位），不是 224 个全做
2. 定时刻：当天日落时刻前后各 2 小时，3 小时步长 → 约 4 个时刻
3. 拉 GFS .idx → 解析出需要的 (变量, 层) 字节区间
4. Range 下载 → eccodes 解析 → 裁海南 10×10 格
5. 沿路径（5 个采样点 × 9 个气压层）双线性插值
6. 取每层自己的 geopotential_height 作为纵坐标
7. 判定地下层 / 缺测层
8. 算太阳几何（含平面投影）
9. 写 data/cross/<机位>-<方位>-<长度>-<时刻>.json（约 30 KB/条）
10. 提交

[前端] 只读 JSON，Canvas 渲染，不做任何气象计算
```

### 6.1 数据量估算

| 项 | 数 |
|---|---|
| 机位 | 8 |
| 方位 | 1（265°，日落方向） |
| 长度 | 1（50 km） |
| 时刻 | 4 |
| 每条 JSON | ≈30 KB |
| **一次产出** | 8×1×1×4 = 32 条 ≈ **1 MB** |
| 每天 2 次 | 2 MB/天，一年 ≈ 0.7 GB |

比现在 `data/forecast/` 的 6.6 MB/次还小，完全可接受。
（且 git delta 压缩后会小很多，实测方法见 `tools/measure-cache-git.mjs`）

### 6.2 缓存策略

- 按 `modelRunTime` 缓存：同一轮起报只算一次
- `validTime` 已过去的条目保留（用于回看和 A 级校验）
- 前端 HTTP 缓存沿用现有 `_headers` 的 5 分钟

## 7. 前端可视化

### 7.1 技术选型（任务书 6.3 要求比较）

| 方案 | 数据量 5×9=45 格 | 渲染性能 | 交互 | 依赖 | 结论 |
|---|---|---|---|---|---|
| **Canvas 2D** | 轻松 | 极快 | 要自己写命中测试 | 0 | ✅ **推荐** |
| SVG | 45 个矩形没问题 | 一般 | 天然支持事件 | 0 | 可行但重绘慢 |
| WebGL | 过剩 | 最快 | 复杂 | 大 | ❌ 45 个格子用不上 |
| ECharts | 能用（heatmap + 自定义） | 中 | 现成 | +1 MB | ❌ 为一个图引 1 MB 不划算 |
| D3.js | 灵活 | 中 | 要自己写 | +250 KB | ❌ 我们不需要它的比例尺/过渡全家桶 |
| Plotly | 能用 | 慢 | 现成 | +3 MB | ❌ 太重 |

**选 Canvas 2D。** 理由：
- 数据只有 45 格，Canvas 画起来毫无压力
- 项目已有大量 Canvas 经验（名片绘制 `src/lib/canvas`、`forecast-card`）
- 零新依赖，符合「不为热门框架增加复杂度」
- 双线性插值后的**平滑云区**用 Canvas 的 `createImageData` 逐像素画最自然，
  SVG/DOM 反而做不好

### 7.2 图层设计（任务书 3.6 要求「不要叠加太多」）

默认只开 2 层，其余手动开：

| 图层 | 默认 | 视觉编码 |
|---|---|---|
| 云水 | ✅ 开 | 蓝绿渐变，透明度 ∝ 混合比 |
| 地形 | ✅ 开 | 底部实心轮廓（灰褐） |
| 云冰 | ❌ 关 | 紫白渐变 |
| 温度 | ❌ 关 | 等温线（每 2 °C），不上满色块 |
| 湿度 | ❌ 关 | 等值线（60/80/90%） |
| 风场 | ❌ 关 | 稀疏风羽（每 2 个采样点放一个） |
| 垂直运动 | ❌ 关 | 上升蓝 / 下沉红的小箭头 |
| 太阳光线 | ✅ 开 | 几何射线 + 方向箭头 |
| 观测者 | ✅ 永远开 | 左下角小人图标 + 高度标注 |

**同屏图层上限 3 个**，超过就提示「图层过多会影响判读」。
这一条是硬性 UI 规则，不是建议 —— 任务书说「不要将过多物理变量叠加到同一张图上」。

### 7.3 桌面端

- 图表占满整行宽度，高度 ≥420 px（**不塞进普通卡片**）
- 完整横纵坐标轴 + 刻度 + 单位
- 鼠标悬浮：显示该格所有变量的精确值 + 该格状态（真格点/插值/地下/缺测）
- 滚轮缩放（时间轴另设，不用滚轮）
- 右上角「全屏」按钮

### 7.4 手机端（任务书 6.2 明确「不允许直接缩小」）

```
做法：图表容器固定宽度 = 视口宽度 × 1.6，外层 overflow-x: auto
      → 用户可以横向拖动看完整剖面，而不是把字缩到看不见

配套：
  · 首次进入时画一个「← 左右拖动 →」的提示，拖动后消失
  · 纵轴（高度刻度）position: sticky left，拖动时始终可见
  · 图例折叠成一个「ⓘ 图例」按钮，点了才展开
  · 关键数字（云顶高度、云水峰值层）在图上方用一行大字给出，
    不用缩放也能看到最重要的结论
  · 触控查看数据：touchmove 时显示十字准星 + 数值气泡
  · 「全屏」按钮在手机上变成「横屏查看」（requestFullscreen + orientation lock）
```

### 7.5 无障碍与降级

- 所有颜色编码都要有第二个通道（图案/文字），不只靠颜色区分云水/云冰
- `prefers-reduced-motion` 时不播放入场动画
- Canvas 不可用时（极老浏览器）显示一个 HTML 表格版的最小数据

## 8. 与现有预测模块的关系（任务书第七部分）

### 8.1 联动（做）

| 现有模块 | 联动方式 |
|---|---|
| 时间切换（今天/明天/日出/日落） | 剖面同步切到对应 `validTime` |
| 决策卡「展开云层剖面」按钮 | 展开后**上方**是这条水平—垂直截面，**下方**保留原 8 行廓线表 |
| 逐小时最佳时刻 | 点某小时 → 剖面切到那个小时 |
| 多模式切换 | 剖面若有多源，同步切换 |

### 8.2 绝不做的联动（红线）

```js
// ❌ 禁止
row.score = f(crossSection.cloudWaterIntegral)
```

理由有三条，任何一条都足够：
1. 现有硬约束 1：`scoreOf` 公式不许动，改分数必须有 A 级证据
2. 任务书第七部分原文：「不能因为剖面图视觉效果更直观，就让它取代原有预测算法」
3. 剖面只有 GFS 单模式，而评分是三家平均 —— 拿单模式替换三模式平均，
   是**降低**信息量

**剖面是解释层。它回答「为什么这个分数是这样」，不参与「分数是多少」。**

### 8.3 但可以做一件事：解释一致性检查

剖面算出的「云顶高度」「云水峰值层」可以用来和评分里的
`cloudBaseLow/cloudBaseMid` 对照，如果长期不符，说明评分里的云层判断可能有问题
—— 这属于**验证手段**，不是改分依据。写进 `tools/` 的诊断脚本里，不上页面。

### 9.1 验证用例（任务书 8.2 要求）

| 天气过程 | 期望图上看什么 |
|---|---|
| 高云覆盖 | 只有 300–200 hPa 有云水/云冰，低层干净 |
| 低云覆盖 | 只有 1000–850 hPa 有云，高层干 |

## 10. 这份方案刻意没承诺的东西

1. **没承诺「连续的高分辨率截面」** —— 5 个格点就是 5 个格点，图上会如实画出
2. **没承诺云的颜色准确** —— 「这层云会被照成什么色」是现有 `vividLabel` 的业务判断，
   剖面不重算辐射传输
3. **没承诺横向连续** —— 横轴是 5 个真实格点 + 插值，不是像素级的连续观测
4. **没承诺 224 个机位全做剖面** —— 先 8 个代表机位，跑通了再看要不要扩
5. **没动任何现有评分代码**
