# 卫星云顶温度（CTT）可行性探查

> 目的：火烧云算法最缺的是「中云量 / 高云量」，模式预报在这两项上技巧很低。
> 静止卫星的红外通道能直接给出云顶亮温 —— 云顶越冷 = 云越高。
> 这里记录 2026-10-25 的实测结论，别再重复踩坑。

## 结论一句话

**技术上拿得到，但工程上不划算。** 免费、免注册的路走不通；
能走通的那条（AWS 上的 Himawari）需要下载 GB 级数据 + 逆向二进制格式，
对一个纯静态站点来说代价太高。

## 逐一验证过的东西

### ❌ 国家卫星气象中心（NSMC）风云数据门户

| 试的地址 | 结果 |
|---|---|
| `data.nsmc.org.cn/DataPortal/cn/data/download.html` | 404 |
| `data.nsmc.org.cn/DataServer/api/data/search?...` | 404 |
| `fy4.nsmc.org.cn/data/cn/FY4B.html` | 404 |
| `img.nsmc.org.cn/PORTAL/.../OperatingGuide/FY4B/` | 403 |

FY-4B 的 CTT（云顶温度）产品确实存在，是
`FY4B-_AGRI--_N_DISK_1330E_L2-_CTT-_MULT_NOM_..._4000M_V0001.NC`，
但下载要经过门户登录 + 「数据申请」流程，**不是公开直链**。
「风云地球」平台同样需要账号。

### ❌ RainViewer 红外云图

`https://api.rainviewer.com/public/weather-maps.json` 返回的
`satellite.infrared` 是**空数组**。直接请求瓦片模板返回 400。
它的红外只覆盖欧洲/非洲，不含中国。

### ✅ AWS 上的 Himawari-9（真能用，但太重）

```
https://noaa-himawari9.s3.amazonaws.com/
```

**实测通了**（匿名、无 key、无注册）：

- 列目录 `?list-type=2&prefix=AHI-L1b-FLDK/2026/10/24/1000/` → 160 个文件
- B13（10.4 µm 窗区红外）分 **10 个块**，共 23 MB
- 下载单块 `HS_H09_20261024_1000_B13_FLDK_R20_S0110.DAT.bz2`
  → HTTP 200，1.18 MB
- bz2 解开 → 5.8 MB，头部确认：`Himawari-9 MSC FLDK H09 20261024 1000 B13`

**坑在哪**：这是 JMA 的私有二进制块格式，
每块 `<BlockNumber><BlockLength><ScanLines><pixels...>`，
但块长字段的语义（含头/不含头、65534 分块上限）需要对照
Himawari 官方文档反复试。我在这里试了 4 轮没能稳定对齐，
再往下就是逆向工程，不是这个项目该做的事。

### ✅ Himawari L2 云产品（能按字节范围读，但文件太大）

```
AHI-L2-FLDK-Clouds/.../AHI-CHGT_v1r1_h09_..._c202308161452133.nc
```

- 文件 **791 MB**（云顶高度 CHGT）、302 MB（云掩膜 CMSK）、82 MB（云相态 CPHS）
- S3 支持 **HTTP Range**：`Range: bytes=0-2047` → `206 Partial Content`
- 格式是 **HDF5**（魔数 `\x89HDF`），不是好处理的 netCDF3

Range 可用意味着「理论上能只读需要的切片」，但 HDF5 的切片读取需要
完整的 chunk index 解析，Node 里没有轻量库能干净地做这件事
（要么 `netcdf4` 的原生依赖，要么 `h5wasm` 的 2 MB WX 包）。

## 如果将来真要做，路线是

1. 用 `h5wasm`（纯 WASM，无原生依赖）在 GitHub Action 里读 HDF5
2. 只读海南/中国范围的 chunk，算出「云顶亮温 < −20℃ 的像素占比」
3. 作为 `data/obs/ctt-<prov>-<date>.json` 存下来（每省几百字节）
4. 进 `check-accuracy.mjs` 当一个独立维度，看它和实际烧不烧的相关性

**代价估计**：每省每天一次 Action 要拉 80–790 MB，GitHub Action 每月
流量有限额（免费额度 2000 分钟/月 + 出站流量），34 个省每天跑会超。
可行的折中是只跑海南一个省验证相关性，验证通过再考虑扩。

## 当前建议

**先不做。** 理由：

1. METAR 才攒了 1 天数据，连「现有算法准不准」都还不知道；
   再引入一个新数据源，没法判断是哪个带来的改进
2. 真要补云量，性价比更高的是「等 METAR 攒够 30 天」——
   它虽然只有机场、只有低云+总量，但零成本、已经在跑
3. CTT 的验证本身也需要 30 天以上的样本才能算相关性

**触发条件**：如果 30 天后 METAR 显示「误报率偏高且集中在
『预报低分但实际有霞』」，说明是云量的问题，那时再做 CTT 才有依据。
