# 少云能烧却被斩杀 · 根因诊断与 v2 优化方案

> 日期：2026-11-07
> 触发：主人授权「为优化可改算法」；用户反馈「较少云量的烧不应该那么低数值和档位」。
> 结论：**问题不是 `fHigh<8→0` 一个点，而是「乘法结构 + 1.8 次方 + Math.round」组合，
>       把高云 0~40% 的「少云」分数系统性压到 0~42 分，全部掉进「不烧/微烧」。
>       正确杠杆是上游画布（杠杆①），不是改指数（杠杆④）。**

---

## 一、根因（用数据 + 代码双重定位）

### 1.1 分数-高云量曲线（铁证）

固定「通透晴天」（low=10 通透、mid=30、aod=0.2、rh=60、pop=0），只变高云量，跑真实 `scoreOf`：

| 高云量 | 分数 | 高云量 | 分数 |
|---|---|---|---|
| 0% | 0 | 50% | 68 |
| 5% | 0 | **55%** | **83（满分）** |
| 8% | 0 | 60% | 83 |
| 10% | 0 | 70% | 83 |
| 15% | 3 | 78% | 83 |
| 20% | 7 | 85% | 51 |
| 30% | 21 | 100% | 7 |
| 40% | 42 | | |

**三个事实**：
1. **高云 0~10% 全是 0 分**——"少云/晴天被斩杀"。注意：这不是 `fHigh<8→0` 一刀切单独造成的（`fHigh(10)=0.04` 本该 >0），而是「乘法结构 + 1.8 次方 + Math.round」把 `raw≈0.03` 压到 `round(100·0.03^1.8)=round(0.2)=0`。
2. **20% 高云只有 7 分、30% 只有 21 分、40% 只有 42 分**——全部够不到"小烧 48"，甚至大部分够不到"微烧 30"。这正是用户说的"较少云量的烧不该这么低"。
3. **55~78% 才是 83 分满分**——`fHigh` 的甜区要求高云量过半，对"薄卷云 20~30% 就能烧"（文献 #4、Mount Washington）太苛刻。

### 1.2 A 级样本分布（220 条）

| 高云量段 | 样本数 | 其中 score=0 | 其中实况 cloudy 且 0 分 |
|---|---|---|---|
| 0~8% | 137 | 122 | 35 |
| 8~20% | 16 | 11 | 5 |
| 20~55% | 33 | 1 | 0 |
| 55~78% | 11 | 0 | 0 |
| 78~100% | 23 | 10 | 4 |

- **144 条（65.5%）score=0**，其中 137 条高云 <8%（`fHigh=0`）。
- **"实况 cloudy（真有中高云）但 score=0" 有 44 条**，其中 35 条高云 <8%、5 条 8~20%、4 条 >78%（这 4 条是厚云被 lowF/wetF 压到 round=0，属另一类）。
- 即：**"少云能烧却被斩杀"的受害者，主要是高云 0~20% 的 40 条 cloudy 样本**（35+5）。

### 1.3 为什么"改指数"救不了（§1.1 已证）

`score = round(100 · raw^1.8)`，`raw=0` 时任何指数都是 0。65.5% 的 0 分样本里，137/144 是 `fHigh=0`（raw 上游就是 0），**改指数对它们完全无效**。这就是 ALGORITHM-COLLAB §1.1 的结论，我复现并认同。

## 二、v2 方案：软化 fHigh 低端斜率（杠杆①）

### 2.1 目标

让「薄卷云/高积云 8~40%（尤其 20~30%）」这个"少云能烧"区间，分数从现在的 0~42 抬到「微烧~小烧」的合理位置，同时**不抬高厚云（>78%）和完全无云（<8% 仍为 0）**。

### 2.2 改法（版本化，红线 1 合规）

在 `scoring.ts` 新增 `formula:'v2'` 路径，v2 的 `fHigh` 低端斜率调缓：

- **v1（现状）**：`h<8→0`；`8~55%`：`(h-8)/47`（8%→0，55%→1）
- **v2（候选）**：低端保留"无云不烧"（`h<5→0`，比 8 略降，因为文献 #2 说模式高估无云），但 5~55% 用更缓的曲线，让 20% 拿到 ~0.4、30% 拿到 ~0.6，而不是现在的 0.26/0.47。

**具体候选曲线**（待 A/B 扫描确定）：

| 版本 | fHigh 低端 | 20% 高云 → | 30% 高云 → | 55% 高云 → |
|---|---|---|---|---|
| v1 现状 | `(h-8)/47` | 0.255 | 0.468 | 1.0 |
| v2a | 缓坡，`(h-8)/30` 到 38% 饱和 | 0.4 | 0.73 | 1.0 |
| v2b | 更缓，`(h-8)/24` 到 32% 饱和 | 0.5 | 0.92 | 1.0 |

### 2.3 风险与验收（红线 2）

- **系统性抬高全站分数** → 必须满足红线 2：平均上浮 <1 分 + 降低 0 条。
- 必须用 A 级样本算误报率，v2 误报 ≤ v1（1.4%），命中 ≥ v1。
- 必须跑 `diff-scores.mjs` 逐机位对比，等级翻转逐条解释。

## 三、与"天空霞"方向的关系

- **天空霞（杠杆②）**：救"高云 <8% 完全无云"的 0 分样本，A 级依据 = 0（见 learning-notes），是**更激进**的方向。
- **本方案（杠杆①）**：救"高云 8~40% 薄云"的 0~42 分样本，有文献 #2（高云 0 不硬归零）、#4（薄云即可烧）的 A/C 级支撑，是**更稳**的方向。

**建议顺序**：先做杠杆①（软化 fHigh 低端），它有更硬的文献依据（#2 是 A 级）、影响面更可控（不碰"完全无云"这个最敏感区）；天空霞作为后续独立 v3 再评估。

## 四、A/B 影响面扫描结果（2026-11-07 实测）

| 版本 | 全站平均上浮 | A 级误报 | A 级命中 |
|---|---|---|---|
| v1 现状 | — | 5（2.5%） | 1 |
| v2a（起坡5 饱和40） | **+2.69 分** ❌ | 9（4.5%）❌ | 1 |
| v2b（起坡5 饱和32） | **+4.13 分** ❌ | 10（5.0%）❌ | 2 |

**红线 2 要求：平均上浮 <1 分 + 误报不劣于 v1。v2a/v2b 双双超标。**

**等级翻转明细（16 条）里藏着致命误报**：绝大多数实况是 `clear`（无云），却因"预报高云 30~45%"被抬到中烧/世纪大烧：

- `ZLLL high=44.7 实况clear → 59→92（世纪大烧）` ← 无云报世纪大烧
- `ZLLL high=43.3 实况clear → 55→92（世纪大烧）`
- `ZLLL high=30.3 实况clear → 21→72（中烧）`

**根因**：模式预报的"高云 30~45%"与实际"无云"误差很大（文献 #2 的"报晴≠真晴"的反面——报云≠真云）。v2 贸然抬升这些样本，等于把"模式的云量误差"直接放大成"误报"。

## 五、最终结论：三条路都验证过了

| 方向 | 杠杆 | 结论 |
|---|---|---|
| 改压缩指数 1.8 | ④ | ❌ 纯亏，救不了 0 分（§1.1） |
| 天空霞（晴空散射） | ② | ⚠️ A 级依据=0，救起的样本 63~75% 实况无云，命中无法验证 |
| 软化 fHigh 低端 | ① | ❌ 平均上浮 2.7~4.1 分 + 误报翻倍，违反红线 2 |

**诚实的判断**：用户反馈的"少云能烧却被斩杀"，根因是**模式对少云的云量预报本身不可靠**（文献 #1/#2 的 TSS 0.47、报晴≠真晴、报云≠真云）。在这个数据质量下，任何"抬升少云分数"的尝试，都会把模式的云量误差放大成误报——这正是红线 2"宁可漏报不可误报"要防的。

**唯一可能正道的方向**：不是改评分公式，而是**提高上游云量判据的可靠性**——比如用卫星云顶高度（`satellite-ctt`，台账里已有，等样本）交叉验证模式的高云量，只在"模式 + 卫星一致认为有薄云"时才抬分。但这需要卫星样本攒够，属于"等数据"的挂起事项，不是现在能做的。
