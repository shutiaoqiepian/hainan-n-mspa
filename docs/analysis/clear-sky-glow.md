# 晴天散射晚霞被"误杀"的物理调研

> 日期：2026-11-07
> 触发：用户反馈「好多天都是烧的云量很低、比较偏晴天，但就是报不烧；一旦云量低了一点，
>       即使光路不被挡也会被直接斩杀到个位数或者 20~30 沦为不烧」
> 结论先行：**根因是 `scoreOf` 把「火烧云」等价于「高云画布」，漏掉了「晴天散射霞光」这一整类
>       真实可拍的晚霞。而这一类霞光的物理，其实已经在 `vividnessOf` 里完整算出来了，
>       只是它没接进评分主线。**

---

## 一、晚霞的两类物理光源（关键概念）

傍晚天空发红（晚霞 / 火烧云）有两个**彼此独立**的光源，缺一个都不该漏掉：

| 类型 | 物理机制 | 需要的条件 | 追霞圈叫法 |
|---|---|---|---|
| **A. 云被照亮** | 太阳落到地平线下，中高云仍从**下方**被低角度阳光照亮，云体本身染红 | 中高云（卷云/高积云）量够、云底能被照亮 | 火烧云、烧云 |
| **B. 大气散射霞光** | 太阳光线斜穿大气，被空气分子 + 气溶胶散射，**天空本身**从蓝变橙红；有少量云做"反光板"更好看，但**没有云也能出霞** | 空气通透（AOD 低）、太阳低、地平线不挡 | 晴天晚霞、火烧天、维纳斯带 |

**当前 `scoreOf` 只算了 A，完全没算 B。** 更糟的是，B 类（晴天、云量低）恰恰会触发
`fHigh` 的 `if (h < 8) return 0`，导致 `h = 0 → scoreOf 直接 return 0`。

这就是用户说的"斩杀"：**物理上能出霞的晴天，因为"高云量 <8%"，被公式在第一步判成 0 分。**

---

## 二、代码层面的精确定位

### 2.1 斩杀链条（`src/lib/forecast/scoring.ts`）

```ts
// fHigh：高云画布
export function fHigh(h: number): number {
  if (h < 8) return 0              // ← 高云 <8% 直接 0
  if (h <= 55) return (h - 8) / 47 // 8%→0，20%→0.26，55%→1
  if (h <= 78) return 1
  return 0.25 + 0.75 * (100 - h) / 22
}

// scoreOfAt 里：
const h0 = clamp(fHigh(high), 0, 1)
const h = lift > 0 && canLift ? clamp(h0 + (1 - h0) * lift, 0, 1) : h0
if (h <= 0) return 0              // ← 无画布 = 0 分
```

用户描述的两种情况：
1. **"斩杀到个位数/0"**：高云 0~8%，且中云 <25%（`midOpacityOf` 里 `mid < minCover` 直接
   `clear`，`lift=0`）→ `h = 0` → `return 0`。
2. **"20~30 分沦为不烧"**：高云 8~20%，`h0 = 0~0.26`，中云补不上 → 分数 ≈
   `0.26 × lowF × midF × aodF × wetF` 再 1.8 次方 ≈ 20~30 分，掉进"不烧"（<30）。

### 2.2 低云"挡不挡光路"根本没进主线

用户说"即使光路不被挡也被斩杀"。低云遮挡在 `scoreOf` 里只以两个**惩罚**形式存在：
- `fLow(low)`：头顶低云，`1 - low/82`，是乘法因子之一（惩罚）；
- `horizonBlock`：太阳方向低云，`raw *= horizonBlock`（惩罚）。

**没有一个是"低云少 + 空气通透 + 太阳低 → 晴天霞光该加分"的正向项。**

### 2.3 关键发现：`vividnessOf` 已经算出了 B 类霞光，只是没接进 scoreOf

`scoring.ts` 的 `vividnessOf`（第 377–413 行，2026-10-25 左右加入的"鲜亮度"指标）：

```ts
// 载体：高/中/低云取最大，低云权重 0.55
const canvas = clamp(Math.max(high, mid * 0.9, low * 0.55) / 60, 0, 1)
// 散射介质：AOD 0.06~0.5 最好
const aodF = aod < 0.06 ? 0.45 : aod <= 0.12 ? 0.78 : aod <= 0.3 ? 1 : ...
// 太阳高度：-6°~+4° 满分
const sunF = el >= -6 && el <= 4 ? 1 : ...
return Math.round(clamp(100 * sunF * aodF * (0.25 + 0.75 * canvas) * lowF * popF * visF, 0, 100))
```

**注意 `vividnessOf` 的 `canvas` 和 `scoreOf` 的 `fHigh` 的本质区别**：
- `fHigh`：只认**高云**，<8% 直接 0 —— 晴天高云少 → 0 分；
- `canvas`：认**高中低三层取最大**，且**即使全晴也有 `0.25` 的底**（`0.25 + 0.75 * canvas`）——
  这一项保证了"天空本身也能发色"。

所以现实是：**晴天晚霞的"颜色有没有出来"，系统已经在"鲜亮度"里给了正确判断（比如"橙金/粉紫"），
但"报不报烧"的"分数"却给了 0。** 用户看到的就是这种割裂：鲜亮度说"橙金"，等级说"不烧"。

## 三、正确的修法（有物理依据，且符合硬约束框架）

### 原则：不改 `scoreOf` 公式形状，只加一个"可选开关"的正向修正项

和现有的 `midLift`（中云补画布）、`horizonBlock`（地平线遮挡）、`rainRelief`（雨停回补）
**同一套路**：往 `ScoreOpts` 里加一个**默认关闭、只增不减**的字段，不传时与历史分数逐位一致。

### 具体方案：新增 `clearSkyGlow`（晴天散射霞）

**触发条件**（B 类霞光的物理判据，全部"宁可漏报"）：

1. **高云画布确实不够**：`high < 8`（只有这时才需要"救"，否则高云本身就在给分）；
2. **地平线不挡**：`horizonBlock` 接近 1（太阳方向干净）——用户强调的"光路不被挡"；
3. **空气通透**：AOD 落在散射霞的甜区（0.06~0.5，太干净只剩蓝、太脏发灰）；
4. **太阳低**：日落/日出前后（太阳高度在 -6°~+8° 区间）；
5. **至少有一点"反光板"或通透天空**：全晴完全无云时，霞光极淡，给最低档；
   有少量中/低云（哪怕 10~20%）时，霞光更明显，给高一点。

**评分量级**（关键：只给"微烧/小烧"级别，绝不凭空造大烧）：

- 目标：让"晴天散射霞"从 0 分抬到 **8~25 分**这个区间（对应"微烧"甚至"小烧"下沿），
  而不是 0 分；
- 上限锁死：**任何情况下不超过 30 分**（不能跨进"小烧 48"这条线，否则就是无中生有地报"烧"）。

### 为什么这是"修正项"而不是"改公式"

- 它只影响 `high < 8` 的那批样本（现在 100% 被判 0 分、即"漏报"）；
- 它**只增不减**（只把 0 分抬成 8~25 分，不会降低任何已有分数）；
- 它**默认关闭**（`ScoreOpts` 里不传该字段时，`scoreOfAt` 与 `scoreOf` 逐位一致，历史快照可复算）；
- 它**锁上限 30**，物理上把"晴天散射霞"限定在"微烧"档，不会碰"小烧"及以上，守住"宁可漏报"。

### 需要同步做的验证（和 midLift 当初一样的流程）

1. `tools/ab-midcloud.mjs` 同款的影响面脚本：确认"平均上浮 < 1 分"且"降低 0 条"；
2. `tools/check-accuracy.mjs`：确认 A 级误报率不升（这批 0 分样本里，有多少实况是 clear 的，
   抬分后会不会变成误报）；
3. `tools/test-boundaries.mjs` / `test-physics.mjs`：新增的开关不影响不传时的历史复算。

## 四、风险与必须先跟你摊牌的

1. **这违反硬约束 1 的"字面"**（"不改 scoreOf 公式"）。但**实质是遵守了它的精神**——
   历史快照复算、只增不减、默认关闭，和 `midLift` 完全同一套纪律。要不要做，需要你明确点头。

2. **误报风险真实存在**。抬分的那批样本里，有一部分实况是"clear（无云）"——晴天无云时，
   散射霞其实很淡、甚至只有"维纳斯带"那种粉蓝带。如果把"晴天无云"也抬到 25 分，
   可能把"根本没有霞"的日子报成"微烧"。**所以触发条件里"至少有一点云（哪怕 10%）"这条很关键**，
   它是区分"晴天有霞"和"晴天没霞"的分水岭。

3. **方向对不对，需要你用实拍经验校准**。你是摄影师，比我更清楚：海南的"晴天晚霞"，
   到底多常出现？有没有"晴到一丝云都没有、天却烧得通红"的情况？这决定了触发条件里
   "云量下限"该定多少。
