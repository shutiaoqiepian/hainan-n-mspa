# 六档阈值重切分析（"不烧区间太大，模仿 SunsetBot"）

> 日期：2026-11-07
> 触发：用户反馈「不烧的区间太大了，我们区间应该模仿 sunsetbot」
> 结论先行：**问题根源不在分界点，而在分数分布本身被压死在地板**。任何「只改阈值」的动作都会碰到三条硬约束，必须先想清楚要哪种效果。

---

## 一、现状：分数分布被压死

`node tools/grade-dist.mjs` 实测（34 省 × 2 时次 × 2 天，896 条）：

| 指标 | 值 |
|---|---|
| 平均分 | **2.92** |
| 中位数 | **0** |
| 最高分 | **73** |
| 0–9 分占比 | **91.52%** |

六档占用：

| 档位 | 阈值 | 样本 | 占比 |
|---|---|---|---|
| 世纪大烧 | ≥92 | 0 | 0%（**死档**） |
| 大烧 | ≥82 | 0 | 0%（**死档**） |
| 中烧 | ≥66 | 2 | 0.22% |
| 小烧 | ≥48 | 9 | 1.00% |
| 微烧 | ≥30 | 15 | 1.67% |
| 不烧 | ≥0 | 870 | **97.10%** |

**核心事实**：「不烧」之所以占 0–29 近三分之一，是因为 97% 的预报分数都在 30 以下。就算把「不烧」砍到 0–9，剩下的 91% 还是会全挤进「微烧」，治标不治本。

### 分数为什么压死：`scoreOf` 的数学结构

`src/lib/forecast/scoring.ts` 里的核心：

```ts
raw = h * lowF * midF * aodF * wetF   // 五个 [0,1] 因子连乘
score = 100 * raw^1.8                  // 1.8 次方再把低分往下压
```

- **乘法结构**：任何一项差，整条分被拖垮，别的项补不回来。
- **1.8 次方**：raw=0.5 时 score=100×0.5^1.8≈28.7；raw=0.3 时≈11.4。分数天然往低段聚。
- **硬性 return 0**：`if (h <= 0) return 0` —— 高云画布为 0 且中云补不上，直接 0 分，其他项再好也白搭。

这是**故意的保守设计**（交接文档反复强调「宁可漏报不可误报」，TCC 误差 0.47 所以必须保守）。它不是 bug，是权衡的结果。

---

## 二、SunsetBot 为什么"不烧"窄 —— 关键差异

SunsetBot 的鲜艳度是 **0 ~ 2.5+ 的连续值**，分界点是**非线性递增**的：

| 区间 | 等级 |
|---|---|
| 0 | 不烧 |
| 0.001–0.05 | 微微烧 |
| 0.05–0.2 | 小烧 |
| 0.2–0.4 | 小到中烧 |
| 0.4–0.6 | 中等烧 |
| 0.6–0.8 | 中到大烧 |
| 0.8–1.0 | 大烧（有瑕疵） |
| 1.0–1.5 | 典型大烧 |
| 1.5–2.0 | 优质大烧 |
| 2.0–2.5+ | 世纪大烧 |

它"不烧"窄（只占 0~0.05，即满量程的 2%），**不是因为它把阈值切得细，而是它的公式能把分数拉到 0.4/0.6/1.0/2.0 这些中高段**。

你们是 **0–100 线性分制**，且公式把分数压死在地板。两者刻度不同、分布不同，**"模仿 SunsetBot 的分界节奏"不能直接套**。

---

## 三、两条路线

### 路线 A：只重切阈值（改动小，但不解决根因）

把六档分界点从 `92/82/66/48/30/0` 重新铺到真实分数空间（0–73），模仿 SunsetBot「低分密集、高分稀疏」：

| 档位 | 现 min | 建议 min | 说明 |
|---|---|---|---|
| 世纪大烧 | 92 | 60 | 顶段 |
| 大烧 | 82 | 46 | |
| 中烧 | 66 | 34 | |
| 小烧 | 48 | 24 | |
| 微烧 | 30 | 14 | |
| 不烧 | 0 | 0 | 收窄到 0–13 |

**优点**：只改 `levels.ts` 的 `LEVELS` 数组，图例、`levelOf`、`gradeRangeOf` 全自动跟随。

**代价 / 风险（必须正视）**：

1. **违背"世纪大烧 92 分"的观测约定**。交接文档挂起事项 `century-tier-threshold` 明确写着：92 分线要**等真实数据出现 ≥92 分**再决定是否动。现在把 92 拉到 60，等于在零观测验证下，把最高荣誉的门槛砍掉 1/3。这直接冲击"宁可漏报不可误报"的第一原则。
2. **误报率恶化**。现在 A 级误报率 1.4% 是建立在"97% 判不烧、极少数判烧"的保守基调上的。把"烧"的门槛从 30 降到 14，大量"本不该报烧"的样本会被抬进"微烧/小烧"，误报率大概率上升——但**具体升多少，需要跑 `check-accuracy.mjs` 回测才能量化**（见第四节待办）。
3. **历史快照复算**。`gradeRangeOf` 的半径 5 是围绕"大烧 82→世纪 92 只隔 10 分"设计的（`RANGE_DELTA` 注释明说）。阈值一变，半径也要跟着重算，否则区间文案会跨档。`test-boundaries.mjs` 第 97–128 行**硬编码了 92/82/66/48/30/0 的断言**，必须同步改。
4. **档位语义漂移**。改了之后，"微烧"代表的是"14–23 分"，跟旧数据、旧截图、用户历史认知里的"微烧"不再是一个东西。交接文档里那些"等 A 级样本"的挂起事项，判定口径也会跟着漂。

### 路线 B：让分数真正 spread 开（治本，但踩"不改 scoreOf"红线）

把 `score = 100 * raw^1.8` 的 1.8 次方调小（比如 1.2），或改乘法结构为"取关键项 + 弱惩罚"，让分数能分布到 0–100 中高段，然后阈值自然不用压得这么狠。

**优点**：真正解决"97% 不烧"的根因，效果最接近 SunsetBot。

**代价**：**直接违反交接文档第 3 章硬规矩「不改 scoreOf 公式」**。这条是"历史快照要能复算"的根基——1.8 次方一动，所有历史分数全部对不上，`verify-cache-diff.mjs`、影子分数、accuracy 存档全要推倒重来。**这条基本不可行，除非你明确要推翻硬规矩并愿意承担全部复算成本。**

---

## 四、我的建议

**先别改阈值。** 理由：

1. 你现在看到的"不烧太宽"，本质是"分数压死在地板"的症状。改阈值是治标，且会**制造误报**，和项目的保守基调背道而驰。
2. 真正该做的是**先量化"把烧的门槛降到多少、误报率会涨到多少"**，用数据说话，而不是拍一个"0-13/14-23/24-33..."的数字。

建议的下一步（都不动线上，纯诊断）：

- [ ] **跑一次"阈值敏感性"扫描**：把"微烧"门槛从 30 逐档下探到 25/20/15，各跑一次 `check-accuracy.mjs`，看 A 级误报率、B 级误报率各变成多少。有了这张表，才能判断"值不值得为让更多天气报烧而牺牲误报率"。
- [ ] **跑一次"分数上探"扫描**：看有没有非"改公式"的办法让分数自然 spread（比如现有的 `midLift`、`rainRelief` 这些"只增不减"的物理修正项，是否还有空间，而不是去动 1.8 次方）。
- [ ] 拿着这两张表，再决定：是重切阈值，还是接受"97% 不烧是保守设计的必然代价"。

---

## 五、如果一定要改阈值，最小正确改法

一旦你拍板重切，必须同步做这五件事（缺一不可）：

1. 改 `src/data/forecast/levels.ts` 的 `LEVELS` 数组。
2. 重算 `RANGE_DELTA`（围绕新档位里最窄的一段重新取半径，保持"区间不跨两档"）。
3. 同步改 `tools/test-boundaries.mjs` 第 97–128 行的硬编码断言（92/82/66/48/30/0 全部替换）。
4. 跑 `node tools/check-accuracy.mjs` 回测，确认误报率没有失控（**这条是硬门槛，失控就回滚**）。
5. 跑 `node tools/grade-dist.mjs`，确认六档里没有新的死档、分布比之前合理。
